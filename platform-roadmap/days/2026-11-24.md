## Log

**Did:**
- Fixed the first bug (step 1, first half): `getReadyForWork` is now `for { select { case <-ctx.Done(): return; case j, ok := <-jobs: if !ok { return }; doJob(...) } }`. `TestGetReadyForWorkStopsOnCancel` passes with `-race`.
- Went through two wrong versions on the way: recursion instead of a loop, then a bare `<-jobs` that printed extra `Result: 0` lines once `jobs` was closed (`go run ./worker-pool 2 4` gave 8 results).
- The full `go test -race ./worker-pool` still fails: 2 data races, the `main.go:55` "Job terminated" goroutine. Expected, and it's the next session's work.

**Learned:**
- A goroutine can only react to cancel while it's blocked in a `select` that has a `ctx.Done()` case. `for j := range jobs` blocks *outside* any select, so a `select`/`default` check inside the loop body never runs while it waits.
- Receiving from a closed, empty channel returns the zero value immediately and never blocks. Inside a `select`, use `j, ok := <-jobs` and return on `!ok`. `range` was doing that check for you.
- Go has no tail-call optimisation: recursing once per job grows the stack. Use `for { select {...} }`.
- Once workers exit when `jobs` runs out, `run` returns in ~200 ms and "Job terminated" stops printing. That goroutine isn't tied to `run` at all, which is the same bug as the race at `main.go:55` seen from the other side.

**Stuck / open:**
- Data race at `phase3-linux-networking/worker-pool/main.go:55`: the sleep + `cancel()` + `Fprintln(output, ...)` goroutine outlives `run`, and nothing waits for it.
- Nit (not done): `getReadyForWork`'s `results` param could be `chan<- int`.

**Mistakes:**
- [concurrency] `select` with `ctx.Done()` + `default` inside `for range ch` doesn't make the receive cancellable: the blocking op has to be a case of the select.
- [concurrency] A bare `<-ch` case in a `select` loop spins on zero values once `ch` is closed. Use `v, ok`.
- [design] Recursion to loop over a channel's jobs (no TCO in Go; the stack grows per job).
