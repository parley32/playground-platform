## Log

**Did:** Step 4. `store` type (map plus `sync.Mutex`, `newStore`, `get`/`set` with `defer Unlock`), injected into `handleConn(store, serverValues, conn)` and `handleCommand(store, line)`. Argument parsing for `SET`/`GET` with usage errors, trimmed key and value. Tests: table with a fresh store per row (seed and stored-value fields), `TestMutex` (50 goroutines released by a `start` channel, `wg.Go`, `-race`), `TestSharedStore` (two `net.Pipe` connections, one store). Mutation-checked: no lock in `set`, no lock in `get`, a `set` that stores nothing or the wrong value, and no client close.

**Learned:** Keep the lock next to the data it guards in one type with methods; lock only around the map access, never around a blocking read. A mutex is tested on the type directly. `t.Fatalf` in a goroutine skips `wg.Done` and hangs the test. `wg.Go` exists in Go 1.25. Comma-ok (`v, ok := m[k]`) tells a missing key from an empty value; writing to a nil map panics, so `newStore` must `make`.

**Stuck / open:** Optional: loopback-TCP test for the EOF branch of `handleConn`. Protocol ambiguity: a stored value equal to an error string is indistinguishable from an error. Step 5 not started.

**Mistakes:**
- [concurrency] First idea was to lock inside `handleConn` whenever a line is read, which would block every client during one client's idle wait; lock only around the map access.
- [design] `set` returned an `error` that could never be non-nil.
- [testing] `newStore` first built the struct without `make`, so the first `set` would panic.
- [testing] Sent test lines without `\n`, so the server waited for the end of the line until the idle timeout.
- [concurrency] Called `t.Fatalf` inside a goroutine, which skips `wg.Done` and hangs.
- [testing] A `done` channel closed by a goroutine that only started the real one passed instantly; the first `SET` test checked only the reply, so a `set` that did nothing still passed.
