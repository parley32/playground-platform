## Log

**Did:** Step 3 done. `run` returns errors (sentinel `errUsage`, `start child: %w`, `child exit with error: %w` on the error received from the Wait goroutine), and `main` prints the error to stderr and exits with `exitCode(err)`. Exit codes: an `*exec.ExitError` passes the child's code through, `exec.ErrNotFound` → 127, `errUsage` → 2, `nil` → 0, other errors → 1. `TestExitCode` table test: nil, a real `sh -c 'exit 3'` (bare and wrapped), not found (wrapped), usage, other. End to end: `sh -c 'exit 3'` → `echo $?` prints `3`; a missing command prints 127; no arguments prints 2.

**Learned:** Whether to pass a child's exit code through depends on the program's role. A wrapper (`time`, `env`, `timeout`) passes it through; a tool for which the child is an internal detail turns the failure into its own error. Shell conventions: 2 = usage, 126 = not executable, 127 = not found, 128+N = killed by signal N. `run` describes what went wrong (wrapped errors), and `main` alone maps errors to an exit code; each kind of failure has to be recognisable (`errors.As` for a type, `errors.Is` for a sentinel). `errors.As(err, &target)`: target is a variable of the exact type in the chain (`*exec.ExitError`, since `Error()` has a pointer receiver), and its address is passed because Go copies every argument. An `ExitError` can't be built by hand, so a test runs a real child. `errors.Join` combines independent errors (with newlines); `fmt.Errorf("...: %w", err)` adds context to one. A unit test of `exitCode` passed while the program still exited 1, so the end-to-end check is still needed.
