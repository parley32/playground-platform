When the timer wins, it runs `syscall.Kill(-pid, SIGKILL)`, treats `ESRCH` as "already exited", then waits on `status` again and returns the child's error. Checked: `sh -c 'trap "" TERM INT; sleep 30'` + `kill -TERM <wrapper>` → exits after about 3 s with `137`, and no `sleep` is left. Thread investigation: the wrapper has 8 threads. The main thread's LWP equals the PID. `ps -L -o lwp,stat,wchan` shows most threads in `futex_do_wait` and one in `do_wait`. `GOMAXPROCS=1` → 6 threads. Adding 3 goroutines that sleep added only 2 threads and a new `ep_poll` thread. Explained it back, and ticked "Processes, threads, scheduling".

**Learned:** On Linux a "PID" is a thread group ID. Each thread is a kernel task with its own TID (LWP), and the main thread's TID equals the PID. The Go runtime runs goroutines (G) on OS threads (M), and an M needs a P (one of `GOMAXPROCS` slots) to run Go code. `sysmon` runs without a P. The runtime creates threads itself, on demand, and never destroys them: idle ones are parked on a futex (`futex_do_wait`). So the count is "the most parallel work so far", not a fixed pool. A goroutine blocked on a channel, mutex or `time.Sleep` is just a struct in a wait queue, with no thread. When it's woken it goes onto a run queue and any free thread runs it. A goroutine in a blocking syscall (`wait4` → `do_wait`) holds its thread, because the kernel blocked the thread itself. The runtime moves that thread's P to another thread so Go code keeps running. Network I/O and timers go through the netpoller: one thread in `epoll_wait` (`ep_poll`) with a timeout set to the next timer's deadline. That's why the TCP server's `conn.Read` doesn't cost a thread per connection. A bounded wait is a `select` between the result channel and a timer. After the KILL you still have to wait, both for the real exit status and to reap the child.
